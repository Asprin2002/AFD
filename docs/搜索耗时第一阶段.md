# 搜索耗时第一阶段：省掉重复计算

日期：2026-10-16。原代码基线：`fc95723`。

本轮保持原来的候选数量、预测场景、预测长度和动作选择规则，先优化程序实现。
已经完成两个原有在线窗口的单进程计时与修改前后对照。
这些时间是 Python 程序在本机的耗时，不是 GPU/PIM 硬件时延。

## 实际测到了什么

输入来自原实验的 `burst_busy_32` 与 `mooncake_8`，沿用各自的
`manifest.json`，保持原始请求长度、到达时间、随机种子和长度先验。
两者都是 4 个候选、2 条完整场景；预测长度分别为 16 和 128。
每次只运行一个模拟实验进程。计时工具记录每次搜索、各部分耗时与调用次数，
并保存每次搜索开始前的状态，便于后续单独复查。

原实现的两个主要浪费是：

1. 没有后台传输，或者后台传输已经结束时，仍反复整理后台队列。
   短输出窗口累计调用约 101 万次，Mooncake 窗口约 588 万次。
2. 每个请求生成一个 token，都重新清点全部历史数据的内存占用，
   同一次检查还重复统计 KV。Mooncake 中 KV 清点本身用了约 31.7 秒。

复制模拟状态只占这两个窗口搜索时间的约 3.4% 和 0.6%，本轮没有优先改它。

## 修改了什么，为什么保持原判断

- **内存占用随数据变化记账。** 预测开始时完整清点一次，随后在数据增长、
  新建副本、释放副本、请求退出时更新。权重和未来增长预留也分别计数。
  仍在原来的位置检查容量，包括单个请求追加 token 之后，避免漏掉中途超限。
  这份记账只在预测重放内启用；返回或异常退出时清除，真实状态仍可直接检查和编辑。
- **传输只整理待完成的任务。** 完成的任务仍保留在历史记录中，供就绪时间查询
  和统计使用，但退出待处理队列。没有待完成任务时，直接按原规则安排前台传输。
  有待完成任务时，保持原来的顺序、前台优先、双向共享规则和抢占边界。
  对过去时间的显式查询保留原来的完整遍历。
- **简化重复的算子区间判断。** 利用每层相同的算子顺序直接判断位置，
  替代每次构造三层位置再遍历。测试枚举了全部合法区间及首、中、末层。

没有缩短预测，没有减少场景，也没有用粗评分替代完整评分。
成本模型仍为 `layout-v4-link-calendar`，候选和预测规则版本保持原值。
原始与修改后的源码哈希分别记录在计时输出中。

解码步评价次数仍为 17,145 次。节省来自实现，不是省略预测或传输。

## 验证与记录

专门测试覆盖共享数据、不同副本、权重分片、按块取整、数据复制前后、
请求退出、缓存释放、容量超限、预测异常退出，以及传输插队后的准确完成时间。
另将两种注意力选择方式下的完整运行与原来的逐次清点方式比较。

实际执行 `python3 -B -m unittest discover -s tests -q`：228 项全部通过，
其中新增 10 项测试。本次完整测试耗时约 127 秒。

运行工具是 `tools/profile_layout_search.py`。
原始记录在本工作树的 `results/search-time-phase1/`，这些生成文件按项目约定不纳入 Git：

- `baseline-source/`：修改前的代码和配置快照。
- `original-online/`：原交接文件、原报告和两个输入清单。
- `baseline-busy/`、`baseline-mooncake/`：本次隔离复测的原版记录。
- `final-busy/`、`final-mooncake/`：最终实现的记录，`timings.json` 内有完全一致检查结果。
- 每个目录的 `decisions.jsonl`：逐次搜索的动作、得分、分项时间、调用次数和规模记录。
- 每个目录的 `metadata.json`：源码哈希、输入哈希、Python 版本。
- `optimized-*` 是本轮中间实现的诊断结果，不作为最终提速数字。
- `plain-baseline.json`、`plain-final.json`：上述关闭分项计时的抽查；
  本地复查脚本保存在同目录的 `time_decisions.py`。

复查时使用新的输出目录，避免覆盖已有记录。例如：

```bash
python3 -B -u tools/profile_layout_search.py \
  --manifest results/search-time-phase1/original-online/mooncake_8-manifest.json \
  --output-dir results/search-time-recheck/mooncake \
  --reference results/search-time-phase1/baseline-mooncake
```

## 目前仍然存在的问题

这一步约提速 2 倍，但单次搜索仍在秒到十几秒量级，尚不能放进真实在线关键路径。
修改后，Mooncake 搜索中约 78% 的时间用于反复计算各层的执行成本。
后续应先研究如何复用候选之间相同的成本计算；任何近似预测或减少搜索量的方案，
都应另行验证动作和收益损失，不能计入本轮的等价实现优化。
