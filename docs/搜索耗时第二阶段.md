# 搜索耗时第二阶段：复用相同的模型计算

日期：2026-10-16。比较起点是第一阶段结束时的实现，保存在
`results/search-time-phase2/phase1-source/`，不是最初的 `fc95723`。

## 修改内容

第一阶段后，两个已测窗口约 71%／78% 的搜索时间仍花在单层成本计算。
本轮把相同输入的计算结果保存下来，在一次搜索内供不同层、不同场景和不同候选复用。

1. **相同运算输入共用结果。** 同一个设备、同一种运算、相同的参与数量和
   硬件参数，直接读取已经计算的结果。Attention 还分别核对读取长度与参与情况。
2. **条件相同的层共用单层结果。** 匹配参与请求的顺序、运算放置、数据区间、
   实际共享关系、设备位置与执行组。第一层、最后一层和相邻层的连接条件分别处理。
3. **候选改变后只复用仍相同的部分。** 改变一个请求后，它所在请求组的输入描述
   会变化，必要时整组重新计算；未变化的另一组可以复用。最后仍重新推进完整的流水线。
4. **空请求组直接使用固定的零结果。** 设备分组的固定整数换算也不再反复生成。

这里保存的是数字结果，不保存物理世界或传输排程。每个候选仍在自己的时间线上
逐步推进，处理准备完成、请求退出、内存检查及逐层传输。预测长度、场景、候选、
组合动作和最终选择规则均沿用原值。

匹配共享关系时使用“哪些访问对应同一份物理数据”，不会把长度相同的私有数据
当成共享数据。每次取用结果都重新查看当时的数据归属和有效运算区间，因此部分层
完成复制、准备时间被推迟、请求参与关系改变时，不会直接取用旧状态的结果。
请求及数据块的名称不影响耗时，但共享与独立的关系、访问顺序保持不变。

运算和单层结果只在一次搜索内保存，结束或异常退出后释放。每类运算最多保存
4,096 项，单层结果最多保存 8,192 项，满后清空并继续精确计算，不淘汰候选。
固定设备分组只使用整数参数，另有最多 1,024 项的独立上限，不保存请求数据。

实现主要在 `elasticafd/layout_cost_cache.py` 与 `elasticafd/layout_aware.py`。
原计算过程保留为 `_compute_*`，方便对照；没有改变计算公式与累加顺序。

## 完整窗口的实测结果

三组沿用原清单：busy 为 32 请求、H=16；Mooncake 为 8 请求、H=128；
Qwen Thinking 为 2 请求、H=256，均为 4 候选、2 条完整场景。
第一阶段 Thinking 的完整基准也在本轮单独补跑，并核对了原在线实验的模型摘要一致。
每次只运行一个模拟实验进程。下表均开启相同的公共函数计时。

| 窗口 | 搜索次数 | 总搜索时间：第一阶段 → 第二阶段 | 本阶段加速 | 单次平均：第一阶段 → 第二阶段 | 单次 P95：第一阶段 → 第二阶段 |
| --- | ---: | ---: | ---: | ---: | ---: |
| BurstGPT busy | 17 | 19.062 → 6.804 秒 | 2.80 倍 | 1.121 → 0.400 秒 | 1.352 → 0.460 秒 |
| Mooncake | 13 | 133.951 → 39.988 秒 | 3.35 倍 | 10.304 → 3.076 秒 | 14.582 → 4.259 秒 |
| Qwen Thinking | 9 | 227.265 → 87.249 秒 | 2.60 倍 | 25.252 → 9.694 秒 | 31.293 → 11.484 秒 |

这是 Python 搜索的本机实测，不是硬件加速比，也不是达到在线时限的结论。
P95 只描述这些小窗口内的决策，不是完整在线服务的总体统计。

39 次决策的全部候选得分、动作、基线预测值、请求结果和除搜索计时外的模型摘要
逐项完全相同。42 个请求全部完成，总计 5,713 个输出 token。
完整预测路径数、解码步评价次数、追加 token 次数和物理传输预约次数也均保持一致。
原来有收益的复制、区间调整与组合动作仍然存在。

非空单层计算的复用比例：busy 98.26%，Mooncake 97.36%，Thinking 95.70%。
最大单次保存数量分别为 708、8,112、8,192 项；Thinking 触及上限后发生重算，
没有因此改变动作或评分。

## 如何避免计时误导

正式比较只记录第一阶段已有的公共函数。新增加的输入匹配、原始计算等辅助函数
可以加 `--detail-cost-functions` 单独剖析，但它会增加额外开销，因此不进入上表。
目录中较早的 `operator-layer-*`、`final-busy`、`final-mooncake`、`final-thinking`
是带额外细项记录的中间测量，不能与上表混用。

另对四份保存的搜索状态关闭全部分项计时，仅测搜索本身。两种实现顺序运行同一份
输入，所有候选得分、动作和基线预测仍完全相同。下表是单次抽查，不是完整窗口统计。

| 搜索时刻 | 第一阶段 | 第二阶段 | 加速 |
| --- | ---: | ---: | ---: |
| busy 第 2 次 | 0.935 秒 | 0.284 秒 | 3.29 倍 |
| Mooncake 第 2 次 | 14.332 秒 | 3.416 秒 | 4.20 倍 |
| Mooncake 最后一次 | 8.021 秒 | 3.412 秒 | 2.35 倍 |
| Thinking 第 8 次 | 18.056 秒 | 7.412 秒 | 2.44 倍 |

原始记录在 `results/search-time-phase2/`，依项目约定不纳入 Git：

- `phase1-source/`、`final-source/`：本次比较前后的代码与配置快照。
- `inputs/`：三组输入清单。
- `baseline-thinking/`：本轮补跑的第一阶段 Thinking 基准。
- `final-common-busy/`、`final-common-mooncake/`、`final-common-thinking/`：上表最终记录。
- 每组的 `decisions.jsonl`：每次动作、完整候选结果、耗时和复用次数。
- 每组的 `timings.json`：统计汇总与完全一致检查。
- 每组的 `metadata.json`：输入、源码哈希与计时模式。
- busy／Mooncake 的第一阶段基准在 `results/search-time-phase1/final-*`。
- `plain-phase1.json`、`plain-phase2.json`、`plain-comparison.json`：关闭分项计时的抽查，
  复查脚本为同目录的 `time_saved_decisions.py`。

新增专门检查覆盖：真实共享与等长私有数据的区别、稀疏窗口重叠、不同层的副本归属
及就绪时间、不同执行组、首末层连接、数据并行、不同稠密分片、请求到达与退出、
有收益的组合动作、异常后清理、保存数量上限，以及命中复用后仍逐层重放传输。

实际执行 `python3 -B -m unittest discover -s tests -q`：242 项全部通过，
其中本阶段新增 14 项测试；完整测试耗时约 125 秒。

重跑时使用新的输出目录，例如：

```bash
python3 -B -u tools/profile_layout_search.py \
  --manifest results/search-time-phase2/inputs/qwen_thinking_2-manifest.json \
  --output-dir results/search-time-phase2/recheck-thinking \
  --reference results/search-time-phase2/baseline-thinking
```

## 当前剩下的问题

搜索仍在数百毫秒到十几秒范围，尚未达到真实在线要求。单层计算提速后，
时间更多花在检查结果能否复用、逐层推进以及安排传输。
Thinking 中，传输相关函数自身的累计耗时已占搜索时间约 46%；
不能继续假定所有耗时都来自运算公式，也不能把后台异步执行视为免费搜索。
后续若减少预测计算或引入近似，仍需单独验证收益损失。
